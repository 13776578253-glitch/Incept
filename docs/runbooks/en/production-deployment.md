# Single-host production deployment and recovery

The supported topology is Nginx → non-root Next.js → private PostgreSQL, with persistent media, drafts and Dashboard SQLite in a shared directory. Media stays behind authorization handlers. Do not add a static Nginx alias for restricted document images. See the [Chinese operating procedure](../zh/production-deployment.md) for exact commands and the [remediation evidence](../../current-task/2026-10-13-production-readiness-remediation.md) for completed local checks.

1. Install Docker, Compose v2 with `up --wait`, Node 24.21.0, GNU tar, util-linux and Certbot. Permit only HTTPS/HTTP and restricted SSH; publish neither PostgreSQL nor the app port. Keep releases under `/srv/incept/releases`, a `current` symlink, shared data owned by container UID/GID 1000, private certificates and backups outside the data directory. Build and test the repository Dockerfile on the workstation for Linux/amd64, then upload the image plus versioned deployment/operations files. The production server must not install dependencies or build the application. Retain the current and previous images.
2. Create a root-readable 0600 `/srv/incept/.env.production` from `deployment/.env.production.example`. Generate three independent strong random hexadecimal credentials locally. Configure the release digest, hostname and absolute directories. Never commit or paste credentials. Proxy forwarding is trusted only through the production proxy, which replaces the headers; do not expose app port 3000.
3. With DNS pointing to the server and port 80 available, obtain the first certificate using Certbot standalone before starting Nginx. Copy certificate/key into `/srv/incept/certificates`. Start private PostgreSQL, run the `migrate` service, then start app/proxy with `up -d --wait`. Only `migrate deploy` is allowed. Existing PostgreSQL volumes do not rerun initialization or rotate passwords when env changes.
4. Install `deployment/certificate-deploy.sh` as a Certbot deploy hook. Reconfigure renewal to the `/srv/incept/acme` webroot, run `renew --dry-run --run-deploy-hooks`, and inspect the installation's renewal timer. Confirm certificate expiry, external HTTPS and TLS configuration on the actual domain. See [Certbot's official renewal guidance](https://eff-certbot.readthedocs.io/en/stable/using.html#renewing-certificates).
5. During a maintenance window, back up the old database and files, copy old document/music media and drafts into the configured shared directories, and move Dashboard SQLite including WAL/SHM and snapshot/override files. Preserve URLs, verify checksums and UID permissions, and retain originals until recovery passes. Images without an accessible published reference are denied.
6. Install the supplied systemd main, backup and monitor units. Docker supervises processes and caps logs at 10MB×3 per container; systemd starts the stack at boot. The monitor checks HTTPS readiness, database connectivity, 15% free disk and backup freshness under 24h. Grant its unprivileged account only the needed read/traverse permissions. Connect failed units to an operator-owned alert destination and test delivery: a journal entry alone does not establish notification delivery.
7. Run a manual backup first, then enable the daily backup timer. The backup script locks scheduling, stops app writes, produces a binary PostgreSQL dump and an archive of the complete shared directory, hashes them, and restarts the app. Stop independent authoring CLIs as well. Copy completed backups to protected off-host storage; retain at least 14 days and remove old copies only after verified off-host upload and recovery sampling.
8. Restore using `scripts/production-backup.mjs --env-file <recovery-env> --project <separate-project> --restore <backup-folder> --confirm-empty-target` into an empty database and an empty data directory. Start PostgreSQL only before restoring; do not migrate first because the dump includes schema and migration history. Checksums and empty targets are enforced. Database/file restoration is not an atomic cross-storage operation: preserve a failed attempt and retry into a new empty target. Verify articles, sessions, publication receipts, SQLite imports, drafts, images and playable audio, and measure RTO/RPO.
9. For release changes, quiesce writes and back up first. Review migration backward compatibility, deploy migrations, change the image/current revision, then restart with `up -d --wait` and perform Guest/Pro/Owner smoke checks. For a compatible schema, switch back to the retained image/revision while preserving shared data. For an incompatible schema, restore the pre-release backup into a separate empty environment, verify it, and only then cut over. Preserve and account for post-backup writes; never use a production `migrate reset` or `down -v`.

Local self-signed TLS and container restart tests do not replace actual cloud firewall, certificate renewal, host reboot, alert delivery, off-host recovery and external mobile-network acceptance. Release stays NO-GO until those checks pass.

## 2026-10-13 automated monitoring and encrypted off-host backup

This section completes the manual wiring above. See [isolated validation](../../../deployment/validation/README.md) for reproducible synthetic checks.

Install Restic 0.19.1 and verify its official SHA256SUMS. Configure a separate SFTP/HTTPS repository using `.env.backup.example` as `/srv/incept/.env.backup` (0600), with a stable unique host ID. Use a dedicated SSH identity, pinned known_hosts, BatchMode=yes and StrictHostKeyChecking=yes. Optional RESTIC_SFTP_COMMAND is passed as Restic's sftp.command option; for example `ssh -F /srv/incept/.secrets/ssh-config incept-backup -s sftp`. Generate an independent 32-byte random password in RESTIC_PASSWORD_FILE (0600), and preserve it in a separate controlled vault for disaster recovery.

After a successful raw backup, initialize a new repository explicitly once:

```sh
sudo node scripts/production-offsite.mjs --env-file /srv/incept/.env.backup \
  --backup /srv/incept/backups/<completed-backup> --init --apply-retention
```

Omit --init for existing repositories. The wrapper verifies both backup SHA256 hashes before upload and runs `check --read-data` before publishing a receipt. Automatic retention is limited to the configured host and incept-production tag: keep 14 days and at least 2 snapshots, preserving unrelated backups. See [Restic retention](https://restic.readthedocs.io/en/stable/060_forget.html). Local raw backups remain private plaintext; manually remove old copies only after remote verification and restore sampling. Unverified/failed copies are never automatically deleted.

Install incept-offsite.service and the updated backup timer, then daemon-reload. The 03:00 timer starts offsite, whose Requires/After first runs the quiescent raw backup; app is resumed before encryption/upload/verification/retention. Manually start incept-offsite.service and inspect both service journals and the published manifest/receipt before enabling the timer.

Use the complete `.env.monitor.example` as `/srv/incept/.env.monitor` (0640 root:incept). Create `/srv/incept/monitor` (0700 incept:incept) and grant the operator only the required read/traverse ACLs. Configure a real trusted HTTPS alert endpoint, all manifest/receipt/state paths, and an optional private bearer-token file. Probes reject redirects, require 15% free disk by default, and require both raw and verified off-host backups within 24 hours.

The receiver accepts JSON POST, acknowledges with 2xx and deduplicates Idempotency-Key. Payload fields are only eventId, service=incept, status=failure/recovered, check=configuration/health/disk/backup (null on recovery), and occurredAt. State is persisted before sending, retries retain their event ID, initial health is silent, persistent failures remind every 60 minutes by default, and recovery sends a separate event. Delivery failure exits nonzero. Trigger a real test failure and confirm receipt with the actual operator before release.

Restore encrypted snapshots with `restic restore <snapshot> --target <new-private-directory> --verify`, check manifest hashes, then use the independent empty-target PostgreSQL/shared-data restore above. Measure real-data RTO/RPO. Keep the repository password and SSH configuration recoverable independently of the original host.

The certificate hook now validates hostname, remaining lifetime and matching keys before replacement; failed Nginx validation/reload restores old files and preserves a private previous directory. Local ACME used real HTTP challenge validation and renewal; production still needs actual domain dry-run, TLS grading and timer verification.

Every Nginx server overrides the image's default access log. Invitation paths, including unprefixed locale redirects, are redacted and query strings omitted. Ordinary pages use same-origin Referrer-Policy so native publication forms retain a valid Origin; invitations use no-referrer. Request error logs use crit to prevent upstream errors exposing credential URLs; diagnose outages through probes, status codes and redacted application logs. Container rotation does not bound host journald: configure a separate host retention cap suitable for its disk.

The provided `deployment/journald-incept.conf` can be installed as `/etc/systemd/journald.conf.d/incept.conf` (0644 root:root). Restart systemd-journald and inspect `journalctl --disk-usage`. It bounds persistent logs to 256MiB, runtime logs to 64MiB and retention to 14 days. This is a host-wide policy: coordinate it with existing services before installation. The local acceptance did not alter global journald settings.

The final Dockerfile separates build gates from production dependency installation. The runtime receives a frozen offline --prod install, Prisma/tsx for migration/content CLI, generated migration executables and the compiled Dashboard Worker; development test tools are absent. After replacing the app container during a release, run `docker compose ... up -d --no-deps --force-recreate proxy` and check readiness/HTTPS so Nginx resolves the new container address. A quiescent backup stops/starts the same container and preserves its address.

## 2026-10-14 workstation builds and release review

Initial delivery uses local Docker `buildx build --platform linux/amd64 --load`, `docker image save -o`, SSH/SCP upload and server-side `docker image load -i`. Verify archive SHA256 and imported image ID. Offline delivery uses the full image ID in Compose; registry delivery uses a repository manifest digest. Image IDs and registry digests differ. Never copy Windows node_modules or an unverified .next folder as the runtime. See [Docker save](https://docs.docker.com/reference/cli/docker/image/save/), [load](https://docs.docker.com/reference/cli/docker/image/load/) and [platform builds](https://docs.docker.com/build/building/multi-platform/).

Develop on local feature/experimental branches, review diffs and migrations, run build gates and a production dependency audit, then test the exact candidate image against independent data. Experiments must not connect to production persistent data. Record commit SHA, architecture, image ID/digest, deployment-bundle hash, test evidence, schema compatibility, previous release and recovery plan. Human release review precedes cutover; build success alone does not deploy.

Upload and verify the candidate, retain the old release, stop writes/authoring CLIs in a short maintenance window, and take/verify a consistent PostgreSQL/SQLite/media backup. Run approved migrations, switch image/current, then check HTTPS, real bilingual documents, identities and media before resuming writes. Do not run two full application stacks on the 2GB host. Compatible schemas permit image/config rollback; destructive migrations or corrupt writes require preserving failed data and restoring into a separate empty environment before cutover. Account for post-backup writes rather than promising zero loss.

Daily/pre-release backups must reach protected encrypted storage in another failure domain, with independent recovery credentials and an actual restore test. Git and images cannot recover live data; local backups cannot survive disk loss. Existing recovery/Restic tools passed isolated tests; real off-host recovery, alert delivery and Caddy integration remain pending. No GitHub Actions/automatic deployment workflow exists yet; future private GHCR delivery may replace SCP without moving builds onto the server.
