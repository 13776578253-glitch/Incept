# 曲目与曲库管理

面向内容维护者。**日常创作都在网页里完成**：上传音频、编辑曲目、管理曲库。命令行只在批量迁移与重建时使用。

规则与理由见 [曲目与曲库改为网页创作](../decisions/zh/music-authoring-in-the-web.md)；迁移工具（内容根、清单、导入器）的规则见 [music-content-import.md](./music-content-import.md)。

## 先理解三样东西

| 东西 | 位置 | 谁能改 |
| --- | --- | --- |
| 数据库 | `music_tracks` / `music_libraries` / `music_library_items` | **网页**（上传与编辑）或批量导入 |
| 发布出去的音频 | `apps/web/public/_music-media/<sha256>.<ext>`（gitignore） | 网页上传或批量导入；两者都按内容寻址 |
| 迁移用的清单与原件 | `MUSIC_CONTENT_ROOT` 下的音频与 `music.json` | 只在批量迁移时使用，日常可以不管 |

一句话：**数据库是真相，镜像按内容寻址，清单只是迁移工具。**

## 第一次使用

```bash
pnpm db:deploy    # 确保迁移已应用
pnpm dev          # 启动站点（曲目与曲库管理在 设置 → 插件，只对 owner 显示）
```

要新增内容的话，**不需要内容根，也不需要清单**：打开设置页就能上传。只有把一批已有目录一次性导入时才需要 [music-content-import.md](./music-content-import.md)。

## 成为 owner

站点没有 owner 登录表单。打开任意页面，按 F12 在控制台执行一次：

```js
await fetch('/api/auth/owner/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    secret: '把 apps/web/.env.local 里的 OWNER_ACCESS_SECRET 填在这里',
  }),
});
```

返回 `204` 后刷新页面即成为 owner（会话 30 天，存在 httpOnly cookie 里）。管理区只对 owner 渲染，写接口另外校验 owner 会话与同源。

## 日常：上传

打开 **设置 → 插件 → 曲目与曲库管理**，在上传区：

| 想做的事 | 怎么做 |
| --- | --- |
| 加几首散装音频 | 「选择文件」多选，或把文件拖进虚线框；用「归属曲库」下拉决定它们进哪个库 |
| 一次导入一个专辑 / 一集播客 | 「选择文件夹」选中整个目录：**第一层目录名就是曲库名**（`01-播客` → 「播客」），缺的曲库会自动创建 |
| 看进度与结果 | 每个文件一行：等待 → 上传中 x% → 完成 / 失败（失败会给出服务器的原因），按顺序逐个上传 |

- 标题、作者、时长从音频标签里读；读不到就用文件名推断标题，之后在表格里改。
- 只接受 `.mp3` / `.wav` / `.flac`，单个文件上限 128 MB，不做转码与分片。
- 同一份内容再次上传不会多占磁盘：镜像按 sha256 命名，命中即复用；但会新增一行曲目（文件名相同则 key 带 `-2` 后缀）。

## 日常：曲目与曲库

所有编辑都是**立即生效**（没有全局保存按钮）：改完即发一个请求，失败会提示并把界面回滚。

| 想做的事 | 怎么做 |
| --- | --- |
| 改标题 / 作者 | 在表格里直接改，改动后按「保存」 |
| 让一首进多个曲库，或退出某个库 | 点亮 / 熄灭「归属」里的 chips。最后一个归属不能熄灭：每首曲目至少属于一个曲库 |
| 调曲目顺序 | 该行的 ↑ / ↓（交换两首的 `position`；一首属于多个库时它们共享同一个顺序） |
| 下架一首 | 「停用」：行仍在，媒体文件保留，随时可以「恢复」 |
| 新增曲库 | 在「曲库」里输入名字 → 「新建」（key 由服务端从名字派生，同名会复用已有的库） |
| 改曲库显示名 | 直接改那一行的输入框 → 「保存」 |
| 调曲库顺序 | 该行的 ↑ / ↓ |
| 停用一个曲库 | 「停用」→ 若它还有曲目，先在下拉里选择**成员移到哪个库**，再确认。最后一个启用的曲库不能停用 |
| 恢复曲库 | 「恢复」 |

搜索框按标题 / 作者 / key 过滤，右侧下拉按曲库过滤；表格可以横向滚动。

## 批量迁移与重建（命令行）

只在下面两种情况用：换机器 / 重建，或者把一整个内容根一次性导入。日常改动不要走这条路径。

```bash
pnpm music:manifest             # 扫描内容根，生成或更新 <内容根>/music.json
pnpm music:import --dry-run     # 报告会做什么，不写任何东西
pnpm music:import               # 执行：按内容寻址复制进镜像，再在单个事务里写数据库
pnpm music:import --validate    # 一致性检查（清单 / 数据库 / 镜像），有问题时退出码为 1
```

**重要：清单导入是权威的。** 网页新增的曲目不在清单里，导入会把它们连同不在清单里的曲库一起**停用**。命令在写入前会列出这类行；看到警告就先确认这次导入确实应该覆盖网页上的内容，否则改用网页继续维护。

## 备份与恢复

- **元数据**：数据库本身。`pg_dump` 一份即可，恢复后关掉内容根里的 `music.json` 也不会影响任何东西。
- **音频**：把 `apps/web/public/_music-media/` 整个目录拷走（按 sha256 命名，可去重、可校验）。原文件如果还在内容根里，也可以直接拷内容根。
- **迁移**：数据库 + 镜像目录一起搬 → `pnpm db:deploy` → 起站即可。需要给迁移工具一份清单时，把内容根接上再跑 `pnpm music:manifest`。
- **没有"从数据库导出清单"的命令**：清单不是产物，用批量迁移时才现生成。
- **镜像里的孤儿文件**：停用曲目不会删媒体。`pnpm music:import --validate` 会报告"没有任何行引用的镜像文件"，确认后再手动删除——这是目前唯一的清理方式。

## 出问题先看这几处

| 现象 | 原因与处理 |
| --- | --- |
| 设置页看不到管理区 | 不是 owner：按上面的控制台步骤登录后重新打开页面 |
| 上传报"Unsupported music file extension" | 扩展名不在 `.mp3` / `.wav` / `.flac` 里 |
| 上传报超过大小上限 | 单个文件超过 128 MB；先转码或裁剪，当前不做分片上传 |
| 上传报"does not exist or is deactivated" | 目标曲库被停用了：先恢复它，或改选别的库 |
| 上传的文件没有出现在播放器里 | 上传进的是停用的库，或浏览器缓存了目录：刷新页面 |
| 「停用」按钮点不动（曲库） | 它是最后一个启用的曲库——至少要留一个 |
| 「恢复」按钮点不动（曲目） | 该曲目没有任何归属：先给它勾一个启用的曲库 |
| 显示"数据库不可用" | 先确认数据库在跑、`DATABASE_URL` 正确；此时界面只读 |
| 导入很慢 | 复用镜像时会整文件重算 SHA-256，耗时与曲库体积成正比，不是数据库慢 |

## 边界

- 删除都是停用：不删行、不删媒体，也不释放磁盘；清理未被引用的镜像文件仍要手动做。
- 上传不支持断点续传、分片与转码；一次一个文件，失败的不会影响后面的。
- 顺序是曲目自己的 `position`，一首在多个库里共享同一个顺序；没有拖拽排序与批量编辑。
- 没有并发编辑保护：owner 单人使用，同时改动同一行时后写者胜出。
- 访问控制与 CDN 属于部署阶段的事，见导入 runbook 的「边界」一节。
