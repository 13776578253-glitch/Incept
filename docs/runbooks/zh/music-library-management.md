# 曲目与曲库管理

面向内容维护者。**日常创作都在网页里完成**：上传音频、编辑曲目、管理曲库。命令行只在批量迁移与重建时使用。

规则与理由见 [曲目与曲库改为网页创作](../decisions/zh/music-authoring-in-the-web.md)；迁移工具（内容根、清单、导入器）的规则见 [music-content-import.md](./music-content-import.md)。

## 先理解三样东西

| 东西 | 位置 | 谁能改 |
| --- | --- | --- |
| 数据库 | `music_tracks` / `music_libraries` / `music_library_items` | **网页**（上传与编辑）或批量导入 |
| 发布出去的音频 | `apps/web/public/_music-media/<sha256>.<ext>`（gitignore，没有第二份） | 网页上传或批量导入；两者都按内容寻址 |
| 迁移用的清单与原件 | `MUSIC_CONTENT_ROOT` 下的音频与 `music.json` | 只在批量迁移时使用，日常可以不管 |

一句话：**数据库是真相，镜像按内容寻址，清单只是迁移工具。**

## 第一次使用

```bash
pnpm db:deploy    # 确保迁移已应用
pnpm dev          # 启动站点（曲目与曲库管理在 设置 → 音乐，只对 owner 显示）
```

要新增内容的话，**不需要内容根，也不需要清单**：打开设置页就能上传。只有把一批已有目录一次性导入时才需要 [music-content-import.md](./music-content-import.md)。

## 成为 owner

站点没有 owner 登录表单。打开任意页面，按 F12 在控制台执行一次：

```js
await fetch('/api/auth/owner/login', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({
    secret: '把 apps/web/.env.local 里的 OWNER_ACCESS_SECRET 填在这里',
  }),
});
```

返回 `204` 后刷新页面即成为 owner（会话 30 天，存在 httpOnly cookie 里）。管理区只对 owner 渲染，写接口另外校验 owner 会话与同源。

## 日常：上传

打开 **设置 → 音乐 → 曲目与曲库管理**，在上传区：

| 想做的事 | 怎么做 |
| --- | --- |
| 加几首散装音频 | 「选择文件」多选，或把文件拖进虚线框；用「归属曲库」下拉决定它们进哪个库 |
| 上传网易云下载的文件 | 直接把 `.ncm` 拖进去：服务端解密成原始 mp3/flac，用内嵌的歌名与歌手建条目，镜像里只存解密后的音频 |
| 一次导入一个专辑 / 一集播客 | 「选择文件夹」选中整个目录：**第一层目录名就是曲库名**（`01-播客` → 「播客」），缺的曲库会自动创建 |
| 看进度与结果 | 每个文件一行：等待 → 上传中 x% → 完成 / 失败（失败会给出服务器的原因）；「完成」还会说明是哪一种成功（已上传 / 复用已有文件 / 已存在未新增 / 已加入该曲库 / 已存在但已停用），按顺序逐个上传 |

- 标题、作者、时长从音频标签里读；读不到就用文件名推断标题。界面显示读到什么就是什么（不提供手改标题，见 B-22）。
- 只接受 `.mp3` / `.wav` / `.flac`，单个文件上限 128 MB，不做转码与分片。其余文件汇总成一行（「首个文件名 等 N 个文件不符合格式要求」，点开可看完整名单），不会被发出去；一个不含任何音频的目录也不会创建曲库。
- **字节必须真的是音频。** 扩展名只是第一道门：服务端会嗅探文件头、真正解析并要求读得出音频流，所以命名成音频的文本或图片会被带原因地拒绝（一个字节都不会进镜像），而命名成 `.mp3` 的 wav 会按 wav 存储与外发。
- **同一份字节再传不会新增任何东西。** 已有行会被复用：同一个曲库回答「已存在，未新增」，别的曲库只补一条归属（「已加入该曲库」）——这就是把已有歌曲放进第二个曲库的正常做法。同一首歌的 `.ncm` 与 `.mp3` 算作同一份字节。
- 只是**相似**、并非逐字节相同（另一种编码、另一个码率）的歌曲会各自成行，该行会标注「疑似重复：《…》」。系统不会自动合并。
- 内容已存在但那一行处于停用时，回答是「已存在但已停用，请先恢复」，并且什么都不改——在表格里恢复它，再传一次即可补上归属。

## 日常：曲目与曲库

所有编辑都是**立即生效**（没有全局保存按钮）：改完即发一个请求，失败会提示并把界面回滚。

| 想做的事 | 怎么做 |
| --- | --- |
| 改标题 / 作者 | 界面上不提供：标签读到什么就显示什么，读不到显示 `-`；标题识别率在导入侧改进（B-22），不靠手改 |
| 彻底删掉一首（或一个空曲库） | 在行上右键 → 「永久删除」→ 确认。曲目与它的归属关系一并消失，镜像文件保留到下面的清理命令执行时；无法撤销 |
| 让一首进多个曲库，或退出某个库 | 打开该行「归属」的下拉，勾选 / 取消勾选即可，连着勾几项时菜单不会关。最后一个归属不能取消：每首曲目至少属于一个曲库 |
| 调曲目顺序 | 该行的 ↑ / ↓（交换两首的 `position`；一首属于多个库时它们共享同一个顺序） |
| 下架一首 | 「停用」：行仍在，媒体文件保留，随时可以「恢复」 |
| 新增曲库 | 在「曲库」里输入名字 → 「新建」（key 由服务端从名字派生，同名会复用已有的库） |
| 改曲库显示名 | 直接改那一行的输入框 → 「保存」 |
| 调曲库顺序 | 该行的 ↑ / ↓ |
| 停用一个曲库 | 「停用」→ 若它还有曲目，先在下拉里选择**成员移到哪个库**，再确认。最后一个启用的曲库不能停用 |
| 恢复曲库 | 「恢复」 |

搜索框按标题 / 作者 / key 过滤，右侧下拉按曲库过滤；表格可以横向滚动。

## 批量迁移与重建（命令行）

只在下面两种情况用：换机器 / 重建，或者把一整个内容根一次性导入。日常改动不要走这条路径。

```bash
pnpm music:manifest             # 扫描内容根，生成或更新 <内容根>/music.json
pnpm music:import --dry-run     # 报告会做什么，不写任何东西
pnpm music:import               # 执行：按内容寻址复制进镜像，再在单个事务里写数据库
pnpm music:import --validate    # 一致性检查（清单 / 数据库 / 镜像），有问题时退出码为 1
```

**重要：清单导入是权威的。** 网页新增的曲目不在清单里，导入会把它们连同不在清单里的曲库一起**停用**。命令在写入前会列出这类行；看到警告就先确认这次导入确实应该覆盖网页上的内容，否则改用网页继续维护。

## 媒体清理（命令行）

网页这边永远不删媒体：失败的上传、停用的曲目、被永久删除的曲目都会把文件留在镜像里。回收"没有任何行引用"的文件：

```bash
pnpm music:cleanup           # 列出（不写任何东西）
pnpm music:cleanup --apply   # 删除它们
```

- **在没有上传进行时执行**——先关掉设置页、确认没有导入在跑。命令自己判断不了是否有写入者，而一个正在进行的上传刚发布、还没提交数据库行时，它的文件看起来也像"没人引用"。
- 它只认内容寻址命名（`<64 位十六进制>.<mp3|wav|flac>`），因此 `.upload.tmp` 与目录里的其它文件都不会被碰。
- `pnpm music:import --validate` 会在清单比对里报告同一批孤儿；真正执行删除的是这条清理命令。

## 备份与恢复

> **镜像目录没有第二份，而且它就躺在仓库工作区里。** `apps/web/public/_music-media/` 是 gitignore 的：git 不跟踪它，也没有任何自动备份。一次「清理工作区」、切分支时的顺手删除、或把目录清空重来，都会让数据库里的行指向不存在的文件——播放器随即拿不到音频（日志里 `/_music-media/*` 全是 404），而且**删掉的文件只存在于那里，找不回来**，只能拿原件重传。动这个目录之前，先按下面第二条把它拷走。

- **元数据**：数据库本身。`pg_dump` 一份即可，恢复后关掉内容根里的 `music.json` 也不会影响任何东西。
- **音频**：把 `apps/web/public/_music-media/` 整个目录拷走（按 sha256 命名，可去重、可校验）。原文件如果还在内容根里，也可以直接拷内容根。
- **迁移**：数据库 + 镜像目录一起搬 → `pnpm db:deploy` → 起站即可。需要给迁移工具一份清单时，把内容根接上再跑 `pnpm music:manifest`。
- **没有"从数据库导出清单"的命令**：清单不是产物，用批量迁移时才现生成。
- **镜像里的孤儿文件**：停用曲目不会删媒体，永久删除也一样，发布之后失败的上传也会把文件留在那里。回收靠 `pnpm music:cleanup --apply`（在没有上传进行时执行）；`pnpm music:import --validate` 会在它的报告里列出同一批文件。

## 出问题先看这几处

| 现象 | 原因与处理 |
| --- | --- |
| 设置页看不到管理区 | 不是 owner：按上面的控制台步骤登录后重新打开页面 |
| 上传列表显示「某文件 等 N 个文件不符合格式要求」 | 这些文件被扩展名过滤掉、没有发送；点那一行可展开完整名单，也没有为它们创建曲库 |
| 上传报"The file is not MP3, WAV or FLAC audio"或"no readable audio stream" | 文件内容不是音频，或只剩容器壳：已被拒绝，从未进过镜像 |
| 上传报"Unsupported music file extension" | 扩展名不在 `.mp3` / `.wav` / `.flac` 里（选择器通常已经过滤掉这类文件；`.ncm` 是第四种被接受的扩展名） |
| 上传显示「已存在，未新增」/「已加入该曲库」/「复用已有文件」 | 不是错误：内容本来就在库里，复用了行或镜像文件——见上面「同一份字节」那几条 |
| 上传显示「已存在但已停用，请先恢复」 | 这份内容对应的行处于停用状态：在表格里恢复它，需要的话再传一次补上归属 |
| 上传报"The file exceeds the 128 MB limit." | 单个文件超过 128 MB；先转码或裁剪，当前不做分片上传 |
| 上传报"does not exist or is deactivated" | 目标曲库被停用了：先恢复它，或改选别的库 |
| 上传的文件没有出现在播放器里 | 上传进的是停用的库，或浏览器缓存了目录：刷新页面 |
| 播放器放不出声、状态显示「音频加载失败」，服务器日志里 `/_music-media/*` 全是 404 | 镜像文件不在了（工作区被清理、切分支时被删、目录被清空等），而数据库的行还在。把原件重新上传一次即可复原：内容寻址会命中同一行，只把文件重新发回来；有备份就直接拷回 `apps/web/public/_music-media/` |
| 「停用」按钮点不动（曲库） | 它是最后一个启用的曲库——至少要留一个 |
| 「恢复」按钮点不动（曲目） | 该曲目没有任何归属：先给它勾一个启用的曲库 |
| 显示"数据库不可用" | 先确认数据库在跑、`DATABASE_URL` 正确；此时界面只读 |
| 导入很慢 | 复用镜像时会整文件重算 SHA-256，耗时与曲库体积成正比，不是数据库慢 |

## 边界

- 停用什么都不删；永久删除只删行与归属、保留媒体。释放磁盘只有 `pnpm music:cleanup` 一条路，而它依赖你在"没有上传进行时"执行。
- 上传不支持断点续传、分片与转码；一次一个文件，失败的不会影响后面的。
- 疑似重复只看归一化字符串与时长：没有音频指纹、没有列表级重复扫描，也绝不自动合并（B-23）。
- "一段内容一行"是数据库规则：同一份字节无论叫什么名字再次上传都不会多出一行；`contentHash` 为空的旧行（该列出现之前导入的）永远不会被匹配。
- 写库失败时，上传会把刚发布的文件留在镜像里成为孤儿（API 绝不删内容寻址文件：另一个并发上传可能已经在复用同一份文件）：由 `pnpm music:cleanup` 在没有上传进行时回收。进程被中断也可能留下 `.upload.tmp`，清理命令不会碰它。
- 顺序是曲目自己的 `position`，一首在多个库里共享同一个顺序；没有拖拽排序与批量编辑。
- 没有并发编辑保护：owner 单人使用，同时改动同一行时后写者胜出。
- 访问控制与 CDN 属于部署阶段的事，见导入 runbook 的「边界」一节。
