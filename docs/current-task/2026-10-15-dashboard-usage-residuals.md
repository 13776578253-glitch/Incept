# 用量审查残余问题整改

## 执行前口径

1. 先读取普通及Zstandard归档的完整会话时间线。没有前序水位时，首事件存在last_token_usage就只计该轮，累计与该轮的差值不归到当前日期，标记会话历史不完整并报告未定位量；没有last时保留首累计但明确标记时间归属不确定。后续正常累计差分不变。
2. 索引事件身份使用来源、会话、模型、时间及各类token，不含会漂移的成本、路径。保存全部路径来源，供原生覆盖判断；缺失会话身份时用标准化来源路径区分不相关文件。每次采集重建全量快照，不引入跨采集的已读集合。Codex缺价时费用为未定价（数值0、不代表免费），保留token并标记missingPricing，不使用含缓存的recordedCost；其它来源记录费用策略不改。
3. 用Node24自带Zstandard解压只读采集`.jsonl.zst`，不解压写回源目录。压缩副本与普通副本共享会话身份、水位与eventId。压缩路径映射到原始`.jsonl`路径，继续覆盖旧索引，损坏归档报告读取问题。

验收覆盖缺前序/缺last、恢复前序、普通转压缩、双副本去重、跨压缩水位、损坏归档、索引路径/成本漂移与重复全量刷新。真实源只读复算，脚本及过程结果写`.scratch/usage-residual-2026-10-15/`；不提交、不制作生产包、不部署。

## [2026-10-15 00:29] - Update by AI完成改动

- Codex首事件有last时只计本轮；仍以首累计建立后续差分水位。未定位的前史不分配到首事件日期，保留明确诊断。若没有last，也没有前序水位，保留累计并标记日期不确定，避免把无法确认的记录静默丢掉。
- 增加historyIncomplete标记，沿事件→会话聚合→Owner/Pro详情传递，检查器显示“历史不完整，早期用量的日期归属不确定。”；缺失前史的条数及未定位量进入采集诊断。找到更早的原始或压缩前序后按真实水位重算。
- 索引eventId不再包括recordedCost；有会话身份时也不包括source_file。多个路径作为sourceFiles保留，原生覆盖任一别名即可消除索引兜底。无会话身份时无法仅凭相同数量断言跨文件同一事件，使用标准化路径区分，避免误吞独立请求。
- 去重每次重建完整事件快照；并未把跨次采集的集合持久化。loader、worker和持久快照都是替换结果，而非把每次采集的旧事件再追加。重复采集回归验证总量和eventId不增长；即便成本或路径变化也保持同一身份。
- Codex缺价记录cost为0且missingPricing为true，Token全部保留在未定价子集，费用汇总不再包括可能重复计费的recordedCost。非Codex仍优先保留有效记录费用；重复行中的有效记录费用可以补齐更早的缺价行。
- `.jsonl.zst`使用本项目Node24的内置解压API，只读解压到内存，保留原始时间和会话身份；压缩/普通副本共享去重及累计水位。压缩来源注册原`.jsonl`别名，因此旧索引和归档文件名别名仍受覆盖过滤。损坏归档被报告，不影响其它有效文件。
