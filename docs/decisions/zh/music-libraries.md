# 音乐曲库

## 状态

已于 2026-09-17 采纳并实现（B-19）。下面的 schema、清单契约、导入语义与播放器接线描述的都是已交付的行为。

## 背景

播放器现在只有一份扁平曲目列表。目录来自 `GET /api/music/tracks`，队列就是这份列表，schema 里没有任何分组。需求是把曲库分成若干具名分组（播客、音乐、精选），并让听众在播放器里切换。

四条约束决定了结果。

1. **`trackKey` 是内容身份。** 曲库只是标签：改名或重新分组都不该改变曲目的 key 或它的媒体。
2. **清单是期望状态。** 导入之所以幂等，是因为清单描述了"应该存在什么"；分组必须并入这个模型，而不是另立一套。
3. **换队列意味着什么由 core 决定。** `tracksLoaded` → `setQueue` 已经定义了它，而播放器可见的列表就是队列。
4. **曲目规模很小。** 几十首、一次拉取，不需要服务端过滤。

## 决策

- **曲库是一行，成员关系是一行。** `music_libraries`（key、title、position、isActive）与 `music_library_items`（libraryId、trackId），并带 `@@unique([libraryId, trackId])`。
- **一首曲目可以属于多个曲库。** 这是选择中间表而不是字符串列的原因：精选与跨库收录是真实需求。
- **曲库内的顺序取自曲目自己的 `position`。** 过滤之后相对顺序自然正确，因此清单不新增排序字段，join 行也不需要 position 列。将来若要每库各自排序，加一个可空列即可。
- **清单增加两个可选字段，且由生成器写入。** 顶层 `libraries: [{ key, title, position }]`；每首曲目 `libraries: ["key", ...]`。两者都不是给手工维护的，见下面"授权方式"。
- **引用了未声明的曲库是错误。** 拼错一个 key 必须报错，而不是静默造出一个新曲库。
- **曲目上空的 `libraries` 数组是错误。** "哪都不属于"几乎总是笔误；省略该字段与显式给空数组含义不同。
- **清单完全没有 `libraries` 时使用隐式默认曲库。** 未标注的曲目落入 key 为 `default` 的曲库；其他曲库与成员关系不动。旧清单因此导入不报错、不挪窝。
- **一旦出现 `libraries`，导入对它即为权威。** 清单里没有的曲库停用而非删除（与曲目一致），成员关系按清单整体重写。
- **API 一次返回曲库与归属。** `GET /api/music/tracks` 返回 `libraries`，并在每首曲目上返回 `libraries` 键数组。适配层保留逐字段校验，并额外拒绝引用未知曲库的曲目。
- **切换曲库就是一次 `tracksLoaded`。** 适配层过滤列表后派发；core 零改动。当前曲目仍在新列表里就继续播放，否则游标落到新队首并继续播放。
- **选中的曲库是偏好。** 走偏好通道持久化，"全部"是一个视图而不是一个曲库。
- **切换器放在展开面板头部**，并包含"全部"视图：一行分段 chips，「全部」在最前，横向滚动而不换行；只有一个曲库时整个切换器不渲染——那时"全部"与它本来就是同一个视图。
- **默认曲库在清单里是机械值，在播放器里本地化。** 生成器把 `default` 同时写成 key 与标题；切换器对这个 key 显示本地化文案（默认 / Default）。
- **文件夹没了且没有任何条目引用时，生成器把该曲库从清单移除并报告**，于是下次导入停用它而不是删除它。磁盘上消失的曲目条目会被保留，所以只要还有旧条目提到这个曲库，它就不会因为删掉文件夹而消失。
- **每首曲目至少属于一个曲库**，因此"全部"与各曲库视图都有确定含义。
- **两条模式只由顶层字段区分。** 没有 `libraries` 的清单是旧清单模式：只创建或重新启用 `default`，只为本清单曲目补成员关系，不删也不停用任何东西。有 `libraries` 的清单是权威模式：曲目省略该字段等价于 `['default']`，且清单必须声明 `default`；未声明的曲库停用；成员关系按清单整体重写。

## 创作方式：文件夹就是曲库（仅 CLI 批量迁移）

> **2026-09-18 起，日常创作在网页里完成**（见 [music-authoring-in-the-web.md](./music-authoring-in-the-web.md)）：上传与编辑直接写数据库与镜像，曲库由界面创建、改名、停用与恢复。下面这套规则描述的是 `pnpm music:manifest` 的批量迁移路径——换机器、重建、一次性导入一批已有目录时才用。

清单是生成的，不是手写的。`pnpm music:manifest` 扫描 `MUSIC_CONTENT_ROOT` 并从目录结构推导归属，所以**新建一个曲库就是新建一个文件夹**。

- **内容根下的第一段路径就是曲库。** `01-播客/episode-01.mp3` 属于"播客"，`02-音乐/album/track.flac` 同样属于"音乐"；更深的目录只是曲库内部的自由组织方式。
- **含音频的首级目录必须带数字前缀。** 写 `01-播客` 而不是 `播客`：前缀让顺序显式，也与 docs 导入器给集合编号的方式一致。未编号的目录、重复的编号、以及两个目录派生出同一个 key，都会让生成器直接报错，而不是被悄悄处理。
- **直接在内容根下的文件属于默认曲库**，因此完全不含曲库信息的清单依然有效。
- **key 由文件夹名转写**（与 `trackKey` 同一套转写规则）；标题默认就是文件夹名本身。
- **数字前缀只决定新曲库的初始顺序，并从 key 与标题里去掉。** `01-播客/` 排在 `02-音乐/` 之前，前缀不进 key；已存在的曲库即使文件夹改了编号也保留自己的 `position`，所以改编号不是重排既有曲库的方式。
- **手写的值仍然优先，但手写的 key 必须真实存在。** 手写的 `libraries` 数组或曲库标题，重跑生成器时与手改的曲目标题一样会被保留；既没有数字文件夹派生、上一版清单也没声明的 key 则直接报错——静默写出它会把一个手误变成曲库，导入端的"引用未声明曲库"再也拦不住。没有文件夹的曲库要先在清单的 `libraries` 数组里声明一次，从下一次重跑起它就算"已声明"。手写仍然是表达"一首属于多个曲库"的唯一方式，文件夹表达不了它。
- **该字段由生成器产出。** `scripts/music-manifest.mjs` 写出 `{ libraries, tracks }`，派生与"和上一版清单合并"的逻辑在 `apps/web/src/server/music/manifest-builder.ts`，手写的标题、顺序与归属因此能跨重跑保留。生成器的 `--root <dir>` 可以扫描 `MUSIC_CONTENT_ROOT` 以外的目录，派生逻辑的验证靠它完成，不必动真实素材。

## 管理界面

> **2026-09-18 起本节所述行为已被取代。** 界面不再是清单的编辑器，而是直接写数据库的内容管理器：上传、曲目增删改、曲库新建/改名/停用都在这里完成，清单哈希与冲突处理已随清单退场。完整规则见 [music-authoring-in-the-web.md](./music-authoring-in-the-web.md)。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 在 `music_tracks` 上加 `library` 字符串列 | 改名要重写所有行，曲库无法排序、无法为空，拼错会静默造库；而且它无法表达"一首属于多个曲库"，这正是本次的决定性需求。 |
| join 行上带每库各自的 position | 在"成员关系只是标签"的阶段不需要；将来加一个可空列是很轻的迁移。 |
| 清单里给每首写成带顺序的对象数组 | 同理，而且会成倍放大创作与校验成本。 |
| 服务端用 `?library=` 过滤 | 曲目只有几十行。一次返回让校验集中在一处，也避免每次切换都多一次往返。 |
| 把曲库做成按 locale 本地化的实体 | 曲目标题本身也不本地化，曲库跟随同一形状。 |
| 让可见列表与队列解耦 | 会改动播放器的核心模型。换列表、由 core 决定后果是本次选定的行为。 |

## 后果

- 切换曲库时，当前曲目若在所选曲库里就继续播放；否则按 core 现有规则，游标落到新队首并继续播放。听众会听到另一首曲子。若实际使用后认为这样不对，"切换即暂停"需要新增一个 core 输入，因为 core 目前无法"替换队列并保持暂停"。
- 停用曲库不会删除曲目或媒体；成员关系在每次导入时按清单重写。
- `--validate` 共报告八类问题：原有五类，加上 `libraryNotImported`、`membershipMismatch` 与 `willDeactivateLibrary`。引用未声明曲库的清单仍是解析阶段的硬错误，不进入问题列表。
- **删文件夹本身不会移除曲库。** 磁盘上消失的曲目条目会被保留，只要还有一条提到该曲库，它就会留着；要让曲库真正消失，得把这些条目也从清单里清掉。
- 播放器列表标题统计的是当前视图，因此选中某个曲库时 `列表（27）` 会变成该库的条数。
- **改曲库文件夹名不等于改名。** 文件夹名是里面每个 `file` 路径的一部分，生成器会当成新文件：产生新的 `trackKey`，而旧条目会留在清单里标记"磁盘上不存在"，并在下次导入时被停用。只想改显示名就改 `title`。
- 生成器、导入 CLI、API、适配层与播放器在 B-19 里一起交付；runbook 的目录布局、校验清单与边界三节随之更新。
