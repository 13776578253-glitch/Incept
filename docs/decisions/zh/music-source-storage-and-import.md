# 音乐来源、存储与导入

## 背景

全站悬浮播放器需要真实音频，而不是一个 mock 曲目模块。仓库里恰好只有一个媒体先例：docs 图片管线。那条管线把原件留在仓库外，把内容寻址的副本发布到 `apps/web/public/_docs-media/`，数据库里只保存最终站点 URL。播放器需要的东西要么照它的形状做，要么给出偏离它的理由。

三个约束决定了最终结果。

1. **播放器运行时挂在 locale 段之上**，因此不能直接读数据库，数据必须以显式输入的形式送达。
2. **`@incept/music-player-core` 无 DOM、无宿主依赖**，它不能知道文件、URL 或存储的存在。
3. **部署未定。** 托管平台的任何能力都不能被假定，包括 HTTP Range。

## 决策

采用 docs 的模式，为播放器建立自己的内容根与管线。

- **原件放在仓库之外**，由 `MUSIC_CONTENT_ROOT` 指定。
- **用清单描述曲库。** `music.json` 中每条曲目显式给出 `trackKey`、相对根目录的 `file`、标题、可选的作者与日期，以及显式整数 `position`。
- **发布按内容寻址。** `scripts/music:import` 把文件复制成 `apps/web/public/_music-media/<sha256>.<小写扩展名>`。相同字节是同一个对象；相同字节但不同扩展名是两个对象。镜像不入库。
- **数据库只保存站点 URL。** `MusicTrack.audioUrl` 存 `/_music-media/<hash>.<ext>`。本机绝对路径**永不**写入数据库，因此替换存储后端不需要改任何一行数据。
- **清单契约把内容变化视为身份变化。** 文件内容变了就换新的 `trackKey`。若同一 key 下的内容发生变化，导入器仍会更新该行，但会记录警告——在旧身份下静默发出新字节，比一次吵闹的导入更糟。
- **core 以 runtime event 的形式接收目录。** `tracksLoaded` 携带曲目列表；重新加载对当前曲目意味着什么由 core 决定，而 core 永远看不到 URL、文件或来自存储层的错误字符串。
- **目录失败不是音频失败。** 存储与网络问题在适配层表现为目录状态。core 的 `errored` 只能由 `audioErrored` 与 `playRejected` 触发。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 把音频提交进仓库 | 每次克隆与部署都要重传整个曲库，而单个无损曲目可超 100 MB。 |
| 把 blob 存进数据库 | 备份与查询会严重劣化，而且并没有解决分发问题。 |
| Git LFS | 主库不再膨胀，但克隆仍要拉全量，且不提供访问控制。 |
| 第三方托管或播客平台 | 作为音源可以，但把分发、可用性与跨域行为交给了第三方。 |
| 建一个 `packages/music-player` 包 | 只有一个消费方，不值得承担 UI 包的 React、Tailwind 与 i18n 配置成本。 |

## 边界

- **音乐按决策就是公开内容。** `public/` 下的文件无法做鉴权，因此在使用本地镜像期间，不具备按曲目分级的能力。
- **本地镜像只是过渡形态，不是分发设计。** 部署平台未定，HTTP Range 未经验证。对象存储加 CDN 是发布必需项；编写语法、数据库字段与播放器契约都被设计成能在替换后保持不变。

## 后果

- 替换后端只需改发布实现与 URL 前缀。清单、CLI 接口与所有数据库字段都原样不动。
- `--validate` 比对清单、数据库与镜像，因此漂移可被发现而不是静默存在。
- 导入是幂等的：内容寻址避免重复复制，`trackKey` 避免重复行。
- 导入器在复用镜像时会校验大小与哈希，因此损坏的镜像会被修复而不是被静默发出。代价是每次导入都要读一遍镜像。
- 文件在磁盘上消失的条目会被**保留**在清单中而非清除，因为清除会让下一次导入把它们在无声中停用。
