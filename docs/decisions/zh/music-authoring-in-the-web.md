# 曲目与曲库改为网页创作

## 状态

已于 2026-09-18 采纳并实现。**本文取代** [music-source-storage-and-import.md](./music-source-storage-and-import.md) 与 [music-libraries.md](./music-libraries.md) 里"清单是期望状态"和"文件夹即曲库"作为**日常创作方式**的部分。那两篇保留的内容仍然有效：数据形状、内容寻址镜像、`trackKey` 身份、API 契约、播放器行为都不变；CLI 管线作为批量迁移与重建工具继续存在。

## 背景

B-19 让曲目与曲库可用之后，创作仍然要经过清单：内容根放文件 → `pnpm music:manifest` → `pnpm music:import`。界面一度只是清单的编辑器，"新建曲库"等于"新建编号文件夹"，删除曲库等于删文件夹。实际使用时这条链路太绕：为加一首曲子要开编辑器、改 JSON、跑两条命令，而界面还得小心不把外部改动覆盖掉（页面加载时的清单哈希、409 冲突）。

需求是相反的：**在网页里直接选文件或文件夹上传，并完成曲目与曲库的完整增删改查。**

## 决策

- **网页是唯一写入路径。** 上传与编辑直接写数据库和镜像，不再经过 `music.json`。清单与 CLI 降级为一次性批量迁移工具：换机器、重建、把一批已有目录导入时用，日常不用。
- **每次编辑就是一次请求，没有全局保存。** 改名、归属、顺序、启用状态各自一个请求；界面做乐观更新，失败就报错并回滚。清单哈希与冲突处理随清单一起退场。
- **上传逐文件、流式落盘。** 一个请求一个文件，请求体是原始字节（不用 multipart：它会把整个文件读进内存）。服务端边写临时文件边算 SHA-256 边计数，超过上限立刻中断并删除临时文件；完成后按内容寻址复用或原子改名进镜像。仍只接受 `.mp3/.wav/.flac`，单文件上限 128 MB。
- **元数据来自音频标签。** 落盘后用 `music-metadata` 读 title / artist / duration（导入器读时长的同一入口），读不到就用文件名推断标题；三者都能在表格里改。上传不因为标签缺失而失败。
- **文件夹上传沿用"第一段目录 = 曲库"的习惯。** 浏览器给出相对路径，第一段目录名（数字前缀剥掉）就是曲库名，缺的库自动创建；选散装文件时由界面指定归属。这条约定只是习惯的延续，不再是系统的规则。
- **`trackKey` 由文件名派生，仍是身份。** 转写规则与生成器共用（`music-key.ts`）：同一文件名再次上传会得到 `-2` / `-3` 后缀。改标题、改归属都不影响身份；改文件名才是新曲目。
- **删除是停用，不是抹除；抹除是一次刻意的例外。** 曲目 `isActive=false`，媒体文件保留，界面上可恢复。**曲库停用前必须为它的成员指定去处**（一次请求内完成转移），最后一个启用的曲库不能停用——因此"每条活跃曲目至少属于一个活跃曲库"这条不变量始终成立，播放器那条读取不会因为界面操作而失败。唯一"真删"的入口是行上的**右键菜单**：两次点击（先出菜单、再确认）才会发 `DELETE`，它会删掉曲目行与成员关系，并且**只有在没有别的行还引用同一个镜像文件时**才删文件——文件可能被多行共用，停用行也仍然占着它的那一份。曲库只有在没有成员、且不是最后一个启用曲库时才能删除，其余情况服务端直接拒绝并把原因显示在菜单里。
- **上传 `.ncm` 时在服务端静默解密。** 网易的加密容器会被整体读进内存、解出它原本的 mp3/flac，然后按该格式的内容哈希入镜像——镜像里永远不存加密字节，同一首歌再上传会复用同一个文件。容器内嵌的元数据优先于音频标签（歌名取 `musicName`，歌手取 `artist` 并用 `, ` 连接），网易云下载的歌因此第一次有了歌手字段而不是空；时长仍由标签读取提供。解码器在 `apps/web/src/server/music/ncm-decode.ts`，移植自 owner 的 `ncm-converter` 库；`.ncm` 只是多了一种被接受的上传扩展名，界面上没有任何开关。
- **列表读取只有一条路。** 管理页用 `listAll*`（含停用行），播放器继续用 `listActiveMusicCatalog()`（单事务快照，活跃行）。路由只做序列化，适配层与播放器零改动。
- **owner 隔离不变。** 管理区只对 `viewer.role === 'owner'` 渲染，写入路由再校验 owner 会话与同源，其余一律 404。它位于设置页的**音乐**分区，与播放器偏好同处一节；该分区在 2026-09-20 之前叫「插件」。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 网页继续编辑清单，只是做得更顺手 | 两套权威（清单与数据库）必然要处理冲突；用户要的是"上传完就在库里"，而不是"上传完还要导入"。 |
| 保留清单为权威，但让网页自动触发导入 | 冲突面更大：外部编辑清单、导入失败、部分导入都会让界面状态与数据库不一致，且用户完全看不到清单。 |
| multipart 上传 | 一个 128 MB 的文件会整块进内存；逐文件原始字节流既能流式落盘，又能顺带算哈希。 |
| 上传时立刻把文件写进内容根 | 内容根是给迁移工具用的：网页创作之后它不再是必需，写进去反而制造第二份真相。 |
| 删除即硬删行与媒体 | 从界面误删无法挽回，而内容寻址镜像一旦删除就得从别处找回原文件。 |
| 停用曲库时自动把成员并入第一个曲库 | 归属是内容决定，不是排序细节；让操作者显式选择目标库，代价只有一次下拉。 |
| 每库独立排序 | 目前 `position` 是曲目自己的属性，一首在多个库里共享一个顺序；要做需要在 join 行上加列，属于后续需求。 |

## 后果

- **内容根不再是网页创作的依赖**：管理区不读 `MUSIC_CONTENT_ROOT`，也不需要 `music.json` 存在。只有跑 CLI 时才需要。
- **数据库成为真相，清单是迁移工件。** 因此没有"从数据库导出清单"的命令：需要迁移时用 CLI 重新生成清单，或直接按 [曲库与曲目管理 runbook](../runbooks/zh/music-library-management.md) 拷贝镜像目录。
- **镜像文件的清理仍然是人工的**：停用不会删媒体，`pnpm music:import --validate` 报告无人引用的文件后再手动删除。删除曲目不会释放磁盘。
- **CLI 会警告。** 清单不认识的行（网页新增）在导入时会被停用，因此 `pnpm music:import` 在真正写入前先列出这类行——用迁移工具之前请先读它。
- **上传的上限与格式仍是硬约束**：128 MB / `.mp3` `.wav` `.flac`；超出即报错，不做分片或转码。
- **并发编辑没有保护**：owner 单人使用，每个请求各自成事务；两个人同时编辑同一行时后写者胜出。

## 边界

- 不做断点续传、分片上传与转码；单文件上限 128 MB。
- 不做媒体的硬删除或清理入口，也不做回收站。
- 不做每曲库独立排序、批量编辑或拖拽排序（顺序是曲目的 `position`，界面上是上下移动）。
- 不做上传进度之外的批量状态：上传按顺序逐个进行，一个失败不影响其余。
