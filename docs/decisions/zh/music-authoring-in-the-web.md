# 曲目与曲库改为网页创作

## 状态

已于 2026-09-18 采纳并实现。**本文取代** [music-source-storage-and-import.md](./music-source-storage-and-import.md) 与 [music-libraries.md](./music-libraries.md) 里"清单是期望状态"和"文件夹即曲库"作为**日常创作方式**的部分。那两篇保留的内容仍然有效：数据形状、内容寻址镜像、`trackKey` 身份、API 契约、播放器行为都不变；CLI 管线作为批量迁移与重建工具继续存在。

## 背景

B-19 让曲目与曲库可用之后，创作仍然要经过清单：内容根放文件 → `pnpm music:manifest` → `pnpm music:import`。界面一度只是清单的编辑器，"新建曲库"等于"新建编号文件夹"，删除曲库等于删文件夹。实际使用时这条链路太绕：为加一首曲子要开编辑器、改 JSON、跑两条命令，而界面还得小心不把外部改动覆盖掉（页面加载时的清单哈希、409 冲突）。

需求是相反的：**在网页里直接选文件或文件夹上传，并完成曲目与曲库的完整增删改查。**

## 决策

- **网页是唯一写入路径。** 上传与编辑直接写数据库和镜像，不再经过 `music.json`。清单与 CLI 降级为一次性批量迁移工具：换机器、重建、把一批已有目录导入时用，日常不用。
- **每次编辑就是一次请求，没有全局保存。** 改名、归属、顺序、启用状态各自一个请求；界面做乐观更新，失败就报错并回滚。清单哈希与冲突处理随清单一起退场。
- **上传逐文件、流式落盘。** 一个请求一个文件，请求体是原始字节（不用 multipart：它会把整个文件读进内存）。服务端边写临时文件边算 SHA-256 边计数，超过上限立刻中断并删除临时文件；完成后按内容寻址复用或原子改名进镜像。仍只接受 `.mp3/.wav/.flac`，单文件上限 128 MB。
- **元数据来自音频标签。** 落盘后用 `music-metadata` 读 title / artist / duration（导入器读时长的同一入口），读不到就用文件名推断标题；三者都能在表格里改。上传不因为标签缺失而失败。
- **文件夹上传沿用"第一段目录 = 曲库"的习惯。** 浏览器给出相对路径，第一段目录名（数字前缀剥掉）就是曲库名，缺的库自动创建；选散装文件时由界面指定归属。这条约定只是习惯的延续，不再是系统的规则。
- **`trackKey` 由文件名派生，仍是身份——针对新内容而言。** 转写规则与生成器共用（`packages/db/src/music/keys.ts`，经 `apps/web/src/server/music/music-key.ts` 转发）：真正的新内容撞上已有名字才会得到 `-2` / `-3` 后缀。由于上传先查内容哈希，同一份字节换个文件名再次上传只会复用已有行，不会产生新 key；改标题、改归属都不会改变已有行的身份。
- **删除是停用，不是抹除；抹除是一次刻意的例外。** 曲目 `isActive=false`，媒体文件保留，界面上可恢复。**曲库停用前必须为它的成员指定去处**（一次请求内完成转移），最后一个启用的曲库不能停用——因此"每条活跃曲目至少属于一个活跃曲库"这条不变量始终成立，播放器那条读取不会因为界面操作而失败。唯一"真删"的入口是行上的**右键菜单**：两次点击（先出菜单、再确认）才会发 `DELETE`，它删掉曲目行与成员关系；镜像文件刻意**不删**——并发上传可能已经在复用它——而曲库只有在没有成员、且不是最后一个启用曲库时才能删除，其余情况服务端直接拒绝并把原因显示在菜单里。
- **媒体回收只有一个入口。** `pnpm music:cleanup` 列出"没有任何行引用"的镜像文件（只认内容寻址命名，因此临时文件与外来文件永远不会被它碰）并用 `--apply` 删除。它应当在没有写入者运行时执行——这正是当前架构自己无法检测的那一条前提；`pnpm music:import --validate` 依旧在清单比对里报告同一批孤儿。代码库里再没有别的地方删除媒体。
- **上传 `.ncm` 时在服务端静默解密。** 网易的加密容器会被整体读进内存、解出它原本的 mp3/flac，然后按该格式的内容哈希入镜像——镜像里永远不存加密字节，同一首歌再上传会复用同一个文件。容器内嵌的元数据优先于音频标签（歌名取 `musicName`，歌手取 `artist` 并用 `, ` 连接），网易云下载的歌因此第一次有了歌手字段而不是空；时长仍由标签读取提供。解出的字节与普通上传共用同一套"先验后发"（在临时文件上解析通过才发布），所以解密出一个放不出声的壳时镜像里什么都不会留下。解码器在 `apps/web/src/server/music/ncm-decode.ts`，移植自 owner 的 `ncm-converter` 库；`.ncm` 只是多了一种被接受的上传扩展名，界面上没有任何开关。
- **格式由字节决定，不由文件名决定。** 扩展名白名单只是第一道门（在读请求体之前就判，store 里保留同一道检查作为兜底），临时文件写下之后：12 字节的文件头嗅探（`fLaC` / `RIFF....WAVE` / `ID3` 或裸帧同步）决定用哪个解析器，`music-metadata` 必须能通过它读出音频流——用 `parseStream` 加上该格式的 MIME 提示来解析，因为 `parseFile` 只信扩展名，会把命名成 `.mp3` 的 wav 读废——而且必须解析出采样率（只剩容器壳或截断的文件不报错但没有采样率），嗅探出的格式同时决定镜像文件名与 MIME。命名成 `.mp3` 的 wav 会存成 `<hash>.wav` + `audio/wav`，与 `.ncm` 按解码格式存储完全一致。文本、图片、以及只剩容器壳没有音频流的文件一律 `400` 拒绝，绝不进镜像；解析成功但没有标签的文件照收，标题回退到文件名。
- **一段内容就是一行。** `contentHash` 上有唯一索引，上传在自己的事务里先查这个哈希：同一个曲库回答 `existing`，别的曲库回答 `membership-added`——复用同一行、只补归属，而不是新增第二行；命中停用行回答 `deactivated` 并且什么都不动（恢复是用户在表格里显式点的那一下）；只有查不到才建行，此时 `trackKey` 仍按 `-2` 后缀规则生成。因此同一份字节无论叫什么名字、以 `.ncm` 还是 `.mp3` 进来、传过多少次，都只有一行；同名但内容不同则各占一行。
- **媒体复用与曲目复用分开报。** 响应里 `mediaStatus`（`published` / `reused`：镜像文件是新写的还是本来就有）与 `trackStatus`（`created` / `existing` / `membership-added` / `deactivated`）各自独立，上传列表逐条显示。看起来像同一首歌的行（标题归一化后相近、歌手不冲突、时长差不超过 `max(3 秒, 5%)`）会作为**疑似重复提示**返回——只提示，绝不合并：同一首的不同编码本来就该各留一行（B-23）。
- **镜像不再信尺寸，写库失败则把文件留给清理工具。** 复用判断改成重新哈希目标文件，而不是比尺寸——被同尺寸错误内容替换过的文件会被修复而不是继续发出去；两个并发上传抢同一个目标时按重哈希收敛（Windows 上 rename 覆盖已存在文件会报 `EPERM`，靠这个绕过）；两个并发上传同一份新内容会在唯一索引上重试一次，最终落在同一行。**发布之后**才失败的请求不会删掉刚写下的文件：另一个并发上传可能已经复用了这份文件、只是还没提交自己的行，此刻按"没有行引用"判定就会删掉一份马上要被引用的文件，留下"库里有曲目、镜像却没有文件"。孤儿留在镜像里，由 `pnpm music:import --validate` 报告，等没有写入者运行时再删除。
- **选择器把"跳过"说出来，而且只用一行。** 客户端在发请求之前就按扩展名过滤，跳过的东西汇总成一行——首个文件名、数量与原因——完整名单点一下就能展开，因此一个装着几百个无关文件的目录不会把面板刷成日志。只有确实带着候选文件的目录才会创建曲库，纯图片/歌词目录不会留下空曲库。
- **列表读取只有一条路。** 管理页用 `listAll*`（含停用行），播放器继续用 `listActiveMusicCatalog()`（单事务快照，活跃行）。路由只做序列化，适配层与播放器零改动。
- **owner 隔离不变。** 管理区只对 `viewer.role === 'owner'` 渲染，写入路由再校验 owner 会话与同源，其余一律 404。它位于设置页的**音乐**分区，与播放器偏好同处一节；该分区在 2026-09-20 之前叫「插件」。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 网页继续编辑清单，只是做得更顺手 | 两套权威（清单与数据库）必然要处理冲突；用户要的是"上传完就在库里"，而不是"上传完还要导入"。 |
| 保留清单为权威，但让网页自动触发导入 | 冲突面更大：外部编辑清单、导入失败、部分导入都会让界面状态与数据库不一致，且用户完全看不到清单。 |
| multipart 上传 | 一个 128 MB 的文件会整块进内存；逐文件原始字节流既能流式落盘，又能顺带算哈希。 |
| 上传时立刻把文件写进内容根 | 内容根是给迁移工具用的：网页创作之后它不再是必需，写进去反而制造第二份真相。 |
| 删除即硬删行与媒体 | 从界面误删无法挽回，而内容寻址镜像一旦删除就得从别处找回原文件。 |
| 停用曲库时自动把成员并入第一个曲库 | 归属是内容决定，不是排序细节；让操作者显式选择目标库，代价只有一次下拉。 |
| 每库独立排序 | 目前 `position` 是曲目自己的属性，一首在多个库里共享一个顺序；要做需要在 join 行上加列，属于后续需求。 |
| 标题相同就合并 | 同一首歌的不同编码本来就该各留一行；自动合并一旦合错就丢版本信息，而且重新上传也救不回来。界面上改为提示，由 owner 决定（B-23）。 |
| 扩展名与内容不符就拒绝 | 按嗅探出的真实格式存储正是 `.ncm` 路径已有的行为，能保证发出去的 MIME 不说谎，也不会因为一次改名就丢掉可播放的文件。 |
| 上传命中停用行时自动恢复 | 恢复是内容决定；一次例行上传就把 `isActive` 翻回去，等于未经确认把曲目塞回播放器。 |
| 在请求路径里删内容寻址媒体（写库失败时，或逐行永久删除时） | 看起来干净，但在并发下不成立：另一个上传可能已经复用了这份文件、只是还没提交自己的行，按"现在没有行引用"判定就会删掉一份马上要被引用的文件。按 hash 做跨请求协调得覆盖 临时落盘 → 发布 → 提交 的完整生命周期；让 API 对媒体只读、回收统一交给清理入口是更稳妥的取舍。 |
| 每个上传都先缓冲再校验 | 逐文件流式落盘正是这条链路的要点；校验在临时文件上、发布之前完成，被拒绝的文件同样不会进镜像。 |

## 后果

- **内容根不再是网页创作的依赖**：管理区不读 `MUSIC_CONTENT_ROOT`，也不需要 `music.json` 存在。只有跑 CLI 时才需要。
- **数据库成为真相，清单是迁移工件。** 因此没有"从数据库导出清单"的命令：需要迁移时用 CLI 重新生成清单，或直接按 [曲库与曲目管理 runbook](../../runbooks/zh/music-library-management.md) 拷贝镜像目录。
- **镜像清理是一条命令，不是副作用。** 停用与删除都保留媒体，失败的上传也会留下文件；`pnpm music:cleanup`（`--apply`）统一回收它们，`pnpm music:import --validate` 依旧在清单比对里报告同一批孤儿。单独删掉一首曲目并不会释放磁盘。
- **"一段内容一行"现在是数据库规则。** 相同 `contentHash` 的第二行会被唯一索引拒绝，因此未来任何写入路径——脚本、迁移、别的管理操作——都必须走复用分支。`contentHash` 为 `NULL` 的旧行（列出现之前导入的）不受影响，去重也永远不会匹配它们。
- **导入工具拒绝自己表达不了的清单。** 把同一段内容分配给两个 `trackKey`、或复用了"仍留在数据库里的行"（清单导入只会停用，不会删除）所持有的内容，都会被明确拒绝并指出两个 key。生成器一侧的缺口登记为 B-23。
- **导入器对成员关系是严格解析。** 写入之后仍解析不出对应曲库或曲目的成员关系会让事务直接抛错，而不是被静默过滤，因此返回的 summary 不会报出并未发生的写入。
- **上传接口的 `mediaStatus` 词表变了**：从 `publish` / `reuse` 改为 `published` / `reused`；存储层内部的状态与导入路径保持原来的词。
- **CLI 会警告。** 清单不认识的行（网页新增）在导入时会被停用，因此 `pnpm music:import` 在真正写入前先列出这类行——用迁移工具之前请先读它。
- **上传的上限与格式仍是硬约束**：128 MB / `.mp3` `.wav` `.flac`；超出即报错，不做分片或转码。
- **并发编辑没有保护**：owner 单人使用，每个请求各自成事务；两个人同时编辑同一行时后写者胜出。

## 边界

- 不做断点续传、分片上传与转码；单文件上限 128 MB。
- 不做回收站，也不做撤销式的逐行删除，界面上没有媒体回收入口：删曲目只删行，释放磁盘靠 `pnpm music:cleanup`。
- 不做每曲库独立排序、批量编辑或拖拽排序（顺序是曲目的 `position`，界面上是上下移动）。
- 不做上传进度之外的批量状态：上传按顺序逐个进行，一个失败不影响其余。
- API 永不删媒体，因此孤儿会积累到 `pnpm music:cleanup` 运行时才回收。这条命令依赖操作者保证"没有写入者"（它自己检测不到），只认内容寻址命名，也不碰 `.upload.tmp`——那可能是正在进行的上传的临时文件。
- 不做音频指纹、也不做自动合并：疑似重复只比较归一化字符串与时长，没有列表级扫描，`contentHash` 为空的行永远不会被匹配（B-23）。
