# Tracks and libraries are authored in the web

## Status

Accepted and implemented on 2026-09-18. **This supersedes** the "the manifest is the desired state" and "a folder is a library" parts of [music-source-storage-and-import.md](./music-source-storage-and-import.md) and [music-libraries.md](./music-libraries.md) as the **daily authoring path**. What those documents still describe holds: the data shape, the content-addressed mirror, `trackKey` as identity, the API contract and the player. The CLI pipeline stays as a bulk migration and rebuild tool.

## Background

B-19 made tracks and libraries usable, but authoring still went through the manifest: drop a file into the content root → `pnpm music:manifest` → `pnpm music:import`. The settings page was only a manifest editor, "create a library" meant "create a numbered folder", and removing one meant deleting a folder. In practice that is too much ceremony for adding a song, and the editor had to defend itself against external edits (the manifest hash loaded with the page, a 409 on conflict).

The requirement is the opposite: **pick files or a folder in the browser and get full create/read/update/delete over tracks and libraries.**

## Decision

- **The web is the only write path.** Uploads and edits write the database and the mirror directly; `music.json` is out of the loop. The manifest and the CLI drop to a one-off bulk tool: use them to migrate or rebuild, not day to day.
- **One edit is one request; there is no global save.** Rename, membership, order and activation each send their own request, the UI updates optimistically, and a failure reports and rolls back. The manifest hash and its conflict handling retired together with the manifest.
- **Uploads are one file per request, streamed to disk.** The body is the raw bytes (not multipart, which buffers the whole file). The server writes a temp file while hashing and counting, aborts and deletes the temp file past the limit, then reuses or atomically renames into the mirror by content address. Still `.mp3` / `.wav` / `.flac` only, 128 MB per file.
- **Metadata comes from the audio tags.** After the bytes land, `music-metadata` reads title / artist / duration (the same entry point the importer uses for duration); a missing tag falls back to the file name, and all three fields are editable in the table. Uploads never fail because tags are missing.
- **A folder upload keeps the "first directory is the library" habit.** The browser gives relative paths, the first segment (numeric prefix stripped) becomes the library name, and a missing library is created; uploading loose files asks for the library instead. This is continuity of habit, not a rule of the system.
- **`trackKey` is derived from the file name and is still identity — for new content.** The transliteration rules are shared with the generator (`packages/db/src/music/keys.ts`, re-exported through `apps/web/src/server/music/music-key.ts`), and a genuinely new piece of content under a taken name gets a `-2` / `-3` suffix. Since the upload checks the content hash first, re-uploading the same bytes under another name reuses the row instead of minting a key; renaming a title or moving memberships never changes an existing row's identity.
- **Deleting deactivates rather than erases, and erasing is a deliberate exception.** A track goes `isActive=false`, its media file stays, and the UI offers a restore. **Deactivating a library requires choosing where its members go** (moved in the same request), and the last active library cannot be deactivated — so "every active track belongs to at least one active library" always holds and the player's read never fails because of a UI action. The one way to erase for good is the row's **right-click menu**: two clicks (menu, then a confirmation) call `DELETE`, which drops the track row and its memberships. The mirror file is deliberately **not** removed — a concurrent upload may already be reusing it — and a library can only be deleted while it has no members and is not the last active one; the server refuses the rest and the menu shows the reason.
- **Media reclamation is one entry point.** `pnpm music:cleanup` lists the mirror files no row references (content-addressed names only, so temp files and foreign files are never touched) and deletes them with `--apply`. It is meant to run while nothing is uploading, which is the one condition this architecture cannot check for itself; `pnpm music:import --validate` keeps reporting the same orphans inside its manifest comparison. Nothing else in the code base deletes media.
- **A `.ncm` upload is decrypted on the server, silently.** NetEase's container is read into memory, decrypted to its original mp3/flac and stored under that format's content hash — the mirror never holds encrypted bytes, and re-uploading the same song reuses the same mirror file. The embedded NetEase metadata wins over the audio tags (`musicName` for the title, `artist` joined with `, `), which is what finally gives a NetEase download an artist instead of an empty field; the tag reader still supplies the duration. The decoded bytes go through the same staged validation as a plain upload (parsed on the temp file, published only if that succeeds), so a container that decrypts into something unplayable leaves nothing behind. The decoder lives in `apps/web/src/server/music/ncm-decode.ts`, ported from the owner's `ncm-converter` library; `.ncm` is simply one more accepted upload extension, with no switch anywhere in the UI.
- **The bytes decide the format, not the file name.** The extension whitelist is only the first gate (checked before the body is read, and kept in the store as the same fallback check); after the temp file is written, a 12-byte header sniff (`fLaC` / `RIFF....WAVE` / `ID3` or a bare frame sync) picks the parser, `music-metadata` must read an audio stream through it — parsed with `parseStream` and that format's MIME type, because `parseFile` trusts the extension and misreads a wav named `.mp3` — the parse must report a sample rate (a container shell or a truncated file parses without error but has none), and the sniffed format names the mirror file and the MIME. A wav uploaded as `.mp3` is stored as `<hash>.wav` with `audio/wav`, the same way a `.ncm` is stored as its decoded format. A text file, an image or a container shell with no audio stream is refused with `400` and never reaches the mirror; a valid file with no tags is accepted, with the title falling back to the file name.
- **One piece of content is one row.** `contentHash` carries a unique index, and an upload looks the hash up inside its transaction: the same library answers `existing`, another library gets `membership-added` — one row that gains a membership, not a second row — a deactivated row answers `deactivated` and is left alone (restoring is the user's explicit click in the table), and only a miss creates a row, where `trackKey` keeps its `-2` suffix rule. Identical bytes are therefore one row however they were named, whether they arrived as `.ncm` or `.mp3`, and no matter how often they are re-uploaded; the same title with different bytes stays a different row.
- **Media reuse and row reuse are reported as two facts.** The response carries `mediaStatus` (`published` / `reused` — whether the mirror file was written or already there) and `trackStatus` (`created` / `existing` / `membership-added` / `deactivated`), and the upload list renders them per file. Rows that look like the same song (normalized title, compatible artist, duration within `max(3 s, 5 %)`) come back as duplicate **hints** — never a merge, because two encodings are legitimately two rows (B-23).
- **The mirror trusts no size, and a failed write leaves its file for the cleanup tool.** The store's reuse check re-hashes the target instead of comparing sizes, so a same-size replacement is repaired rather than served forever, and two uploads of the same bytes racing for one target settle on the same file (a rename clash is resolved by re-hashing, because Windows answers `EPERM` on rename-over-existing); two concurrent uploads of new content retry once on the unique index and land as one row. A write that fails **after** publishing does not delete the file it just wrote: a concurrent upload may already have reused that file and not yet committed its row, so an immediate reference check can read "nothing references it" and delete a file that request is about to point at — leaving a track whose file is gone. The orphan stays, `pnpm music:import --validate` reports it, and it is removed later, when no writer is running.
- **The picker skips out loud, in one line.** The client filters by extension before sending anything and summarises what it skipped — the first file name, the count and the reason — with the full list one click away, so a folder holding hundreds of unrelated files does not turn the panel into a log. It creates a library only for folders that carry at least one candidate, so a folder of images or lyrics leaves no empty library behind.
- **There is one read path for playback.** The admin screen uses `listAll*` (deactivated rows included); the player keeps using `listActiveMusicCatalog()` (single-transaction snapshot, active rows only). Routes only serialize, and the adapter and player are untouched.
- **Owner isolation is unchanged.** The block renders only for `viewer.role === 'owner'`, and the write routes re-check the owner session plus same-origin, answering 404 to everyone else. It lives in the settings page's **Music** section together with the player preferences; that section was named Plugin until 2026-09-20.

## Rejected alternatives

| Alternative | Why not |
| --- | --- |
| Keep editing the manifest from the web, just smoother | Two authorities (manifest and database) force conflict handling; the ask was "upload it and it is in the library", not "upload it and then import". |
| Keep the manifest authoritative but let the web trigger the import | A wider conflict surface: external manifest edits, failed imports and partial imports all desynchronise the UI from the database, and the user never sees the manifest. |
| Multipart upload | A 128 MB file lands in memory in one piece; one raw-byte stream per file both streams to disk and hashes on the way. |
| Write the uploaded file into the content root | The content root serves the migration tool; once the web authors content it is not needed, and writing there creates a second truth. |
| Deleting rows and media as the default action | A mis-click would be unrecoverable and a content-addressed mirror entry cannot be rebuilt without the original file, which is why deactivation stays the default and erasing sits behind a right-click menu plus a confirmation. |
| Auto-merging members into the first library on deactivation | Membership is a content decision, not an ordering detail; asking costs one dropdown. |
| Per-library ordering | `position` belongs to the track today, so a track in two libraries shares one order; doing it per library needs a column on the join row and is a separate ask. |
| Merging on a matching title | Two encodings of one song are legitimately two rows; a wrong automatic merge loses the version and cannot be undone by re-uploading. The panel hints instead and the owner decides (B-23). |
| Rejecting an extension/content mismatch | Storing by the sniffed format is what the `.ncm` path already does, keeps the served MIME truthful, and never loses a playable file to a rename. |
| Auto-restoring a deactivated row when its content is uploaded | Restore is a content decision; flipping `isActive` during a routine upload would put a row back into the player without anyone asking. |
| Deleting content-addressed media in the request path (a failed write, or a per-row delete) | It reads as tidy but is unsound under concurrency: another upload of the same bytes may have reused that file and not yet committed its row, so a reference check taken now can delete a file that request is about to point at. Coordinating per hash would have to cover the whole temp → publish → commit lifecycle; keeping the API read-only on media and reclaiming through the cleanup entry is the safer trade. |
| Buffering every upload to validate it before writing anything | The streaming path is the point of one-file-per-request; validation runs on the temp file before it is published, so a rejected file still never enters the mirror. |

## Consequences

- **The content root is no longer a dependency of web authoring**: the admin block does not read `MUSIC_CONTENT_ROOT` and does not need `music.json`. Only the CLI does.
- **The database is the source of truth and the manifest is a migration artefact.** There is no "export the manifest from the database" command: to migrate, regenerate the manifest with the CLI or copy the mirror directory as described in the [library management runbook](../../runbooks/en/music-library-management.md).
- **Mirror cleanup is a command, not a side effect.** Deactivation and deletion keep media, and a failed upload leaves its file; `pnpm music:cleanup` reclaims all of them (`--apply`), while `pnpm music:import --validate` keeps reporting them in its manifest comparison. Deleting a track does not free disk space by itself.
- **One `trackKey` per piece of content is now a database rule.** A second row with the same `contentHash` fails at the unique index, so any future write path — a script, a migration, another admin action — has to go through the reuse branches. Rows with a `NULL` hash (imported before the column existed) are exempt, and dedup never matches them.
- **The import tool refuses what it cannot represent.** A manifest that assigns one piece of content to two `trackKey`s, or that reuses content still held by a row which stays in the database (a manifest import only deactivates), is refused with both keys named. The generator side of that gap is B-23.
- **The importer resolves memberships strictly.** A planned membership whose library or track key cannot be resolved after the writes makes the transaction throw rather than being filtered out, so the returned summary can never report a write that did not happen.
- **The upload API's `mediaStatus` vocabulary changed** from `publish` / `reuse` to `published` / `reused`; the store's internal status and the import path keep their own words.
- **The CLI warns.** Rows the manifest does not describe (added in the web) are deactivated by an import, so `pnpm music:import` lists them before it writes anything. Read that output before using the migration tool.
- **The limits stay hard**: 128 MB, `.mp3` / `.wav` / `.flac`, an error past that; no chunking and no transcoding.
- **Concurrent editing is unprotected**: one owner, one transaction per request; if two edits touch the same row, the later write wins.

## Boundaries

- No resumable or chunked uploads, no transcoding; 128 MB per file.
- No trash or undo for the per-row delete, and no media reclamation inside the UI: deleting a track removes rows only, and `pnpm music:cleanup` is the command that frees disk.
- No per-library ordering, no bulk editing, no drag-and-drop (order is the track's `position`, moved with up/down buttons).
- No batch status beyond upload progress: uploads run one after another, and a failure does not stop the rest.
- The API never deletes media, so orphans accumulate until `pnpm music:cleanup` runs. The tool trusts the operator to run it while nothing is uploading (it cannot detect a live writer), it only considers content-addressed names, and it does not touch `.upload.tmp` files — those may belong to an upload in flight.
- No audio fingerprint and no automatic merge: duplicate hints compare normalized strings and duration only, there is no list-level duplicate scan, and rows without a `contentHash` are never dedup targets (B-23).
