# Incept 第一版架构规划

## 1. 当前判断

`D:\code\Incept-o` 的问题不在于仓库根结构，而在于 `apps/web` 过早进入了复杂壳层设计：

- 导航系统过重，顶部导航、侧边栏、设置入口、内容模式切换彼此耦合
- 响应式策略过重，同一套页面为了适配多个断点引入了太多状态和变体
- 页面壳先于业务闭环成型，导致“结构很多，主流程不清”
- `packages/db` 目前非常轻，并不是当前主要负担

因此，`D:\code\Incept` 第一版不采用“继续修旧前端”的思路，而采用：

**保留轻量 monorepo 形态，按 web-first 重新开始。**

---

## 2. 第一版核心原则

### 2.1 保留的东西

- 保留 `pnpm workspace`
- 保留 `apps/` 作为未来多入口扩展位
- 保留 `packages/` 作为未来共享能力扩展位

### 2.2 暂不引入的东西

- 不预先拆 `packages/db`
- 不预先做 Docker 开发链路
- 不预先做复杂 docs shell / dashboard shell
- 不预先做“大一统”侧边栏状态机
- 不预先为未来多主题、多产品线设计复杂共享层

### 2.3 第一版目标

第一版只解决一个问题：

**让 `apps/web` 能在简单、可读、可持续重构的前提下，跑通一个最小核心流程。**

---

## 5. 这次前端必须遵守的边界

### 5.1 布局边界

第一版页面壳只允许存在三层：

- 顶部导航
- 主内容区
- 可选的简单侧栏

限制：

- 设置页必须是独立路由，不进入侧边栏模式切换
- 文档页、工作页、设置页不共用复杂超级壳
- 侧边栏如果存在，只做导航，不做内容模式管理

### 5.2 响应式边界

第一版响应式只做两种形态：

- 移动端：顶部栏 + 抽屉
- 桌面端：顶部栏 + 单列内容，或简单左侧导航

不做：

- 超宽屏专用逻辑
- 多段折叠面板
- 跟随断点变化的大量布局状态切换

### 5.3 状态边界

布局层状态尽量控制在以下范围：

- `isMenuOpen`
- `theme`
- 可选的 `activeNav`

不允许第一版出现：

- 多个布局模式并存
- 为设置页、文档页、工作页分别维护壳层状态机
- 组件内部大量 `useEffect + useMemo + breakpoint state` 组合控制布局

## 6. 模块职责

### 6.1 `app/`

职责：

- 路由入口
- 页面装配
- 尽量薄，不承载复杂逻辑

### 6.2 `features/`

职责：

- 按业务场景组织代码
- 每个 feature 自己持有组件、hook、数据转换逻辑

规则：

- 通用逻辑不明确之前，不要提前抽到 `components/` 或 `lib/`
- 只有两个以上 feature 共享时，再考虑抽公共层

### 6.3 `components/`

职责：

- 真正跨 feature 复用的 UI 和布局组件

规则：

- `components/ui` 放基础视觉组件
- `components/layout` 放顶栏、容器、页面框架
- 不把强业务组件丢进全局 `components`

### 6.4 `lib/`

职责：

- 工具函数
- 常量
- mock 数据
- 与外部系统的轻量适配

规则：

- 第一版先不要把业务逻辑堆进 `lib`

---

## 7. 数据与服务策略

第一版建议：

- 先用 `mock-data.ts`
- 先把主流程和页面结构跑通
- 数据库能力暂不抽成 `packages/db`

只有满足下面任一条件时，再考虑外提：

- 已经明确存在第二个消费者
- 数据模型趋于稳定
- 需要独立维护 schema / client / migrations

在那之前，数据相关逻辑可以先留在 `apps/web` 内部。

---

## 8. 国际化与主题策略

第一版建议默认从简：

- 主题：可保留 light/dark，但只保留最小切换
- 国际化：如果不是刚需，先单语

如果后续确认双语是核心能力，再加：

- `src/app/[locale]/...`
- `next-intl`

但不要在第一版为了国际化把整体路由壳复杂化。

---

## 9. 第一版页面范围

第一版只做 3 个页面层级：

1. 首页 `page.tsx`
2. 核心工作页 `workspace/page.tsx`
3. 设置页 `settings/page.tsx`

预期作用：

- 首页负责说明产品与入口
- 工作页负责跑通主流程
- 设置页负责承载独立配置，不参与布局状态切换

---

## 10. 从旧仓库迁移时的取舍原则

可以迁移：

- 少量视觉样式变量
- 命名方式
- 少数真正清晰的基础组件
- 文案和内容结构灵感

不要迁移：

- 旧侧边栏状态模型
- 旧 docs shell
- 旧导航下拉和多层响应式逻辑
- 为未来预留但当前没有真实需求的目录与抽象

原则：

**迁移素材，不迁移包袱。**

---

## 11. 第一阶段执行顺序

建议按这个顺序推进：

1. 建立仓库根结构
2. 初始化 `apps/web`
3. 搭最小 `layout + home + workspace + settings`
4. 用 mock data 跑通核心主流程
5. 只在主流程稳定后，再考虑数据库、国际化、共享包

---

## 12. 当前结论

`Incept` 第一版不应该是“完整产品架构”，而应该是：

**一个保留 monorepo 扩展空间、但以单一 `web` 应用为中心的轻量前端重构版本。**

第一优先级不是“架构正确性”，而是：

- 页面更简单
- 代码更可读
- 改动更敢动
- 主流程先成型
